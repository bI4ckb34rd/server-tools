# 🛰️ سرورهای تانل و فورواردر — راهنمای بهینه‌سازی

> ترجمهٔ فارسی — نسخهٔ مرجع انگلیسی است: [TUNNELS.md](TUNNELS.md)

این راهنما برای سرورهایی است که ترافیک را **عبور می‌دهند** نه اینکه خودشان سرویس بدهند:
سرور ایران که با iptables/nftables پورت را به سرور خارج فوروارد می‌کند، دو سر تانل GRE/IPIP/SIT/VXLAN،
گیت‌وی وایرگارد، و تانل‌های userspace مثل Backhaul، Rathole، gost، frp، Chisel، WaterWall، udp2raw و kcptun.

> خلاصه: ServerTools نقش سرور را تشخیص می‌دهد (`tunnel`، `relay`، `vpn`، `utunnel`) و تنظیمات را
> مخصوص همان نقش می‌چیند. هر تصمیم با دلیلش در `st --dry-run` نمایش داده می‌شود.

---

## ۱) چرا روی تانل GRE فقط یک هسته بالا می‌رود؟

هدر بیرونی GRE و IPIP **پورت ندارد**؛ فقط IP مبدأ و مقصد دارد. کارت شبکه برای پخش بسته‌ها بین صف‌ها (RSS)
از همین فیلدها hash می‌گیرد، و چون همهٔ بسته‌های یک تانل بین دو IP ثابت‌اند، همه در **یک صف** و روی **یک هسته** می‌افتند.
این مستقل از تعداد صف کارت شبکه است.

راه‌ها، از بهترین به ساده‌ترین:

1. **کپسوله‌سازی FOU/GUE** (GRE داخل UDP با پورت مبدأ متغیر): کارت شبکه خودش بار را پخش می‌کند و هزینهٔ نرم‌افزاری ندارد.
   این تغییر در ابزار سازندهٔ تانل انجام می‌شود (هر دو سر باید هماهنگ باشند)، مثلاً:

   ```bash
   ip fou add port 5555 ipproto 47
   ip link add gre1 type gre remote PEER_IP local LOCAL_IP ttl 255 encap fou encap-sport auto encap-dport 5555
   ```

2. **RPS** (پخش نرم‌افزاری): ServerTools وقتی تانل GRE/IPIP بدون FOU ببیند، یا کارت شبکه فقط یک صف داشته باشد، خودش روشنش می‌کند.

## ۲) «بعد از بهینه‌سازی همهٔ هسته‌ها مساوی شدند ولی مجموع مصرف بالاتر رفت» — چرا؟

این گزارش کاربر باعث بازطراحی نسخهٔ 2.4.5 شد. سه دلیل دارد که باید از هم جدا شوند:

| دلیل | توضیح | خوب یا بد؟ |
| --- | --- | --- |
| گلوگاه برداشته شد | اگر آن یک هسته قبلاً روی ۱۰۰٪ بود، بسته دور ریخته می‌شد. حالا ترافیک بیشتری رد می‌شود و طبیعتاً CPU بیشتری مصرف می‌شود. | خوب — اگر سرعت کاربران بیشتر شده |
| هزینهٔ خود RPS | هر بسته روی دو هسته پردازش می‌شود و یک وقفهٔ بین‌هسته‌ای (IPI) دارد. روی VPS هر IPI یعنی خروج از ماشین مجازی. | هزینهٔ واقعی |
| تنظیمات مخصوص نود پروکسی روی فورواردر | نسخه‌های تا 2.4.4 روی رله هم RFS، صف `fq` و XPS «همه‌هسته→همه‌صف» می‌گذاشت. بستهٔ فورواردی سوکت محلی ندارد، پس این‌ها فقط هزینه‌اند. | باگ نسخه‌های تا 2.4.4 — در 2.4.5 رفع شد |

نسخهٔ 2.4.5 روی سرورِ فقط-فورواردر: `fq_codel` به‌جای `fq`، RFS خاموش، XPS دست‌نخورده، و اگر ۴ هسته یا بیشتر و یک صف باشد،
هسته‌ای که وقفهٔ کارت شبکه را می‌گیرد از RPS بیرون می‌ماند.

کارت شبکهٔ چندصفی هم ممکن است به دلیل دیگری «یک هستهٔ داغ» نشان دهد: بدون irqbalance همهٔ وقفه‌های دریافت
ممکن است روی هستهٔ ۰ بمانند. وقتی `--diagnose` این را اندازه بگیرد، Quick Optimize وقفه‌ها را یکی‌یکی روی هسته‌ها پخش
می‌کند (پخش سخت‌افزاری، بدون پرش RPS)؛ با `irq_affinity=off` خاموش می‌شود.

### اندازه‌گیری، نه حدس

```bash
st --diagnose
```

در ~۳ ثانیه نشان می‌دهد: softirq، system و steal هر هسته؛ بسته در ثانیه و drop هر هسته؛ صف‌ها و ماسک RPS/XPS؛
drop صف؛ فشار conntrack؛ و MTU تانل‌ها. هیچ چیزی تغییر نمی‌دهد.

### آزمایش A/B (در ترافیک مشابه مقایسه کنید)

```bash
st --set rps_mode=off && st --auto
```

```bash
st --set rps_mode=auto && st --auto
```

```bash
st --set rps_cpus=1-3 && st --auto
```

بعد از هر مرحله `st --diagnose` بگیرید. معیار درست «مصرف CPU به ازای هر مگابیت» است، نه درصد CPU به‌تنهایی.

## ۳) MTU و MSS — دلیل پنهان مصرف CPU

هر کپسوله‌سازی چند بایت اضافه می‌کند. اگر MTU تانل از «MTU کارت − سربار» بزرگ‌تر باشد،
بسته‌ها تکه (fragment) می‌شوند یا گم می‌شوند — یعنی هم کندی و هم CPU بیشتر.

| نوع | سربار (IPv4) | MTU حداکثر روی کارت 1500 |
| --- | --- | --- |
| GRE | 24 | 1476 |
| GRE + FOU | 32 | 1468 |
| IPIP / SIT | 20 | 1480 |
| ip6gre | 44 | 1456 |
| VXLAN / Geneve | 50 | 1450 |
| WireGuard | 60 (IPv6: 80) | 1440 (1420) |

`st --diagnose` و منوی Network tools → `t` همین جدول را برای تانل‌های سرور شما حساب می‌کنند.
ServerTools هرگز MTU تانل را خودش عوض نمی‌کند (مالک تانل، ابزار سازندهٔ آن است و تغییر یک‌طرفه تانل را قطع می‌کند)؛ فقط مقدار درست را می‌گوید.

**MSS clamping** از نسخهٔ 2.4.5 برای نقش‌های `vpn`، `tunnel` و `relay` خودکار در Quick Optimize اعمال می‌شود:
اندازهٔ سگمنت TCP را هنگام SYN با MTU مسیر هماهنگ می‌کند تا اصلاً تکه‌تکه شدنی رخ ندهد.

## ۴) مسیر سریع فوروارد (nftables flowtable) — اختیاری

بزرگ‌ترین صرفه‌جویی CPU برای رله‌ها: بعد از چند بستهٔ اول هر اتصال، بقیهٔ بسته‌ها مستقیم از ingress فوروارد می‌شوند
و از routing و زنجیره‌های netfilter عبور نمی‌کنند.

- منو: Network & VPN Tools → `f`
- نیازمند `nft` و کرنل ≥ 4.17 با `nf_flow_table` (اگر پشتیبانی نشود، بدون هیچ تغییری رد می‌شود)
- ⚠️ بسته‌های offload‌شده از شمارنده‌های iptables و محدودیت‌های مبتنی بر آن (مثلاً حجم‌سنجی با iptables) رد نمی‌شوند.
  اتصال‌های جدید همچنان کامل فیلتر می‌شوند.
- با Rollback یا همان گزینه حذف می‌شود.

## ۵) فایروال روی سرور تانل

UFW به‌طور پیش‌فرض بستهٔ فورواردی را drop می‌کند و GRE را نمی‌شناسد. نسخهٔ 2.4.5 هنگام راه‌اندازی UFW،
اگر نقش فورواردر ببیند، پیشنهاد `DEFAULT_FORWARD_POLICY=ACCEPT` می‌دهد، GRE را از IP طرف مقابل تانل باز می‌کند،
و پورت وایرگارد را خودکار مجاز می‌کند. پروفایل Anti-abuse هم دیگر شبکهٔ تانل (مثلاً `10.x/30`) و شبکهٔ داکر را نمی‌بندد.

**NOTRACK** فقط برای ترافیکی است که مقصدش خود سرور است (`--dst-type LOCAL`)؛ پورت‌هایی که DNAT می‌شوند — شامل قوانین
nft، multiport و رنج — خودکار مستثنا هستند. روی رله‌ای که همهٔ پورت‌ها را فوروارد می‌کند، NOTRACK اعمال نمی‌شود.

## ۶) دستورهای پیشنهادی

سرور ایران (رله‌ی DNAT + GRE):

```bash
st --auto --role relay,tunnel
```

سرور خارج (سر دیگر تانل + نود Xray):

```bash
st --auto --role proxy,tunnel
```

تانل userspace (Backhaul/Rathole/gost):

```bash
st --auto --role utunnel
```

اگر تشخیص خودکار درست باشد، `st --auto` به‌تنهایی کافی است — `st --dry-run` نشان می‌دهد چه چیزی تشخیص داده شده.
